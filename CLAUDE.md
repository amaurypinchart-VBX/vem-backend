This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

VEM (ViewBox Event Manager) — internal project management platform for Viewbox International SA (event installation industry). Manages the full lifecycle of event "chantiers": preparation, installation, dismantling, client handover, logistics. Backend + frontend are the same repo/deployment.

The user (Amaury Pinchart) applies changes manually via copy-paste in github.dev and deploys through Railway's auto-rebuild on push. He is non-technical: prefer full drop-in code blocks over diffs/patches when asked to change something, and keep explanations short — see his instructions at the top of the conversation.

## Deployment (Railway)

- Auto-deploys on push to `main` via Dockerfile build (`railway.toml`).
- The Dockerfile `CMD` runs `npx prisma db push --accept-data-loss && node dist/index.js`, **but `railway.toml`'s `startCommand` (`node dist/index.js`) overrides it on Railway, so `db push` does NOT run at boot in production.** There are no versioned Prisma migration files. To add a table/column: add it to `prisma/schema.prisma` (keeps the Prisma client typed) **and** create it with idempotent SQL in `src/utils/migrations.ts` (see the `plan2ds` / `plans_model_versions` blocks). New models are accessed as `(prisma as any).model` in routes because the Prisma client in `node_modules` is committed to git and only regenerated in the Docker build.
- `node_modules/` and `dist/` are committed to git (historical); the Docker build ignores them (`.dockerignore`) and reinstalls/rebuilds. Don't run the root `npm run build` just to type-check (it rewrites tracked `dist/` files) — use `npx tsc --noEmit -p .`.
- The Dockerfile has a first stage (Node 22) that builds `plans/` into `public/plans`; the backend stage copies it in. That stage only sees `plans/` plus `src/services/structureAiGuard.ts` (copied explicitly, imported by `plans/tests/structure/*.test.ts`, which `npm run build` type-checks): any other file outside `plans/` imported by `plans/` code or tests must be added there too, or the Railway build fails.
- Anything `db push` can't express safely at boot (new enum values, dropping/renaming constraints, backfills, data-preserving column type changes) is handled by hand-written **idempotent raw SQL** in `src/utils/migrations.ts`, run once at server startup via `runStartupMigrations()` (called from `src/index.ts`). Every statement there must be safe to re-run on every boot (`IF NOT EXISTS`, `ADD COLUMN IF NOT EXISTS`, guarded `DO $$ ... $$` blocks, etc.). When adding a schema change that `db push` won't handle cleanly, add a new idempotent block at the bottom of `runStartupMigrations()` rather than writing a Prisma migration.
- Health check: `GET /health`.
- A recurring, misleading symptom: a push doesn't take effect. Before assuming a code bug, verify on github.com that the commit actually landed and that Railway's deployed commit hash matches it — Railway rebuilds don't guarantee the push was received.

## Architecture

**Single Express app serves both the API and the frontend** (`src/index.ts`). No separate frontend build/deploy — `express.static` serves `public/` and a catch-all `app.get('*', ...)` returns `public/index.html` for client-side routing.

- All API routes are mounted under `/api/v1/...` in `src/index.ts`, each as its own router in `src/routes/*.ts`.
- `authMiddleware` (`src/middleware/auth.ts`) is applied per-mount in `index.ts`, not globally — a few routers are intentionally public and mounted *without* it:
  - `/api/v1/public/handover-sign` — client-facing signature link
  - `/api/v1/public` (publicCalendar) — public planning display for warehouse screens
  - `/webhooks` — Brevo inbound email webhook (auth via shared secret checked inside the route, not middleware)
  - `/api/v1/translate`
- `requireRole(...roles)` (same file) is used for extra restriction beyond plain auth (currently only on `/api/v1/assistant`).
- Route handler convention: every handler is `async (req, res, next) => { try { ... } catch (err) { next(err); } }`, responses are `{ success: true, data }` / `{ success: false, error }`, errors are thrown as `new AppError(message, statusCode)` (`src/utils/AppError.ts`) and centrally formatted by `src/middleware/errorHandler.ts` (which also special-cases Prisma `P2002`/`P2025`).
- `src/config/database.ts` exports a single `prisma` singleton (cached on `global` in dev to survive ts-node-dev reloads).
- Real-time: a single Socket.IO server (`io`, exported from `src/index.ts`) — clients join `user:<id>` and `project:<id>` rooms; emit from routes/services to push live updates (e.g. task/ticket changes) to connected clients.
- Inbound email → project/booking automation: `src/services/imapPoller.ts` polls Gmail via IMAP on an interval and feeds `src/services/projectFromEmail.ts` / `src/services/bookingFromEmail.ts`. Can be triggered manually via `POST /api/v1/imap-poll` (admin, from browser console) instead of waiting for the interval. Outbound email goes through a Google Apps Script relay (`src/services/emailService.ts`) — the relay responds with 302 redirects, so the client follows redirects on GET but only re-sends POST on 307/308 (avoids 405s on the echo URL).
- AI features go through `src/services/aiService.ts` (`anthropicRequest` / `callClaude` / a schema-validated JSON variant), model configurable via `ANTHROPIC_MODEL` env (defaults to Claude Haiku). Callers must pass a generous `max_tokens` and check `stop_reason === 'max_tokens'` — a response truncated mid-JSON is a known recurring failure mode for report/summary generation (`assistantService.ts`, `briefingAI.ts`).
- File uploads (photos, PDFs, attachments) go through Cloudinary via `src/services/cloudinaryService.ts` / `src/routes/upload.ts`.
- PDF generation (handover docs, daily reports) is in `src/services/pdfService.ts` via `pdfkit`.
- Check-list de montage (handover): `src/routes/checklists.ts` (mounted at `/api/v1/checklists`) — a template library per phase (`preparation` / `installation` / `dismantling`, tables `checklist_categories` / `checklist_template_items`, filled by `POST /checklists/templates/seed` from `src/services/checklistLibrary.ts`) and one checklist per project and phase (`project_checklists` + items / photos / status logs). Configuring copies the chosen template points into the project (snapshot: editing the library never changes a project). Status rules (comment required for partial / nok / na, OK refused on a photo-required point without a photo) live in the route; stats and the full read used by the handover live in `src/services/checklistService.ts`. `GET /handover` and `GET /handover/:id` return `checklistSummary` (installation phase). The handover shows the installation checklist: PDF section after the zones (`renderChecklistSection` in `pdfService.ts`, data from `checklistPdfData`, N.A. points grouped on one line, 2 photo thumbnails per point, dates in Europe/Brussels), the public signature page (`publicChecklist`: no N.A. points, no ids/e-mails), and `POST /handover/:id/signature-token` answers 409 (`data.checklist`, `canForce`) while critical points are open or points are still pending — only admin / technical_manager can pass `force: true`. Phase `preparation` (points to check before installation, category « Préparation et réception du site ») is shown in the project's Infos tab, never in the handover (card `loadChecklistCard(id, 'prep')`, called from `loadProjectDetail`); it was split out of `installation` by a one-shot migration (marker `checklists.preparationSplit` in `app_settings`). Point attachments live in `project_checklist_photos` with `kind` = `photo` | `document` (`POST /checklists/items/:id/documents`, PDF / Office): only photos count for « photo obligatoire », the PDF and the public page show photos only. Frontend: `public/js/15-checklists.js` (library page, project cards in the Infos and Handover tabs, config modal, full-screen fill view `openChecklistFull`, handover sheet section, signature warning).

### Plans Viewbox (`plans/` → served at `/plans/`)

Separate Vite + React 19 + TypeScript (strict) sub-app, built into `public/plans` (gitignored) by the Dockerfile, opened from the project page (Fichiers or Infos › Modèles 3D › « 📐 Plans Viewbox », `openPlansViewbox` in `01-core.js`). Goal: SketchUp model → vector architect drawing sets (phased spec P0–P7; P0 ingestion/inspector, P1 viewer/isolation/captures, P2 2D engine, P3 sheet editor, P4 dimensioning and P5 PDF export done; see git log for current phase). A saved analysis opens a workspace with tabs Contrôle (inspector) · Vue 3D · Vues 2D · Planches A1 · Étude structure (`ui/Workspace.tsx`).

- `plans/src/core/` — pure, tested logic: classification rules (editable in the app, stored in `app_settings` key `plans.classificationRules`), units/dimension checks, triangle cleanup, manifest.
- `plans/src/ingest/` — browser pipeline: unzip → COLLADA parse (three 0.186 `ColladaParser`/`ColladaComposer` subclassed to keep SketchUp definition names; unit + Z-up applied exactly once) → geometry cleanup in a Web Worker → scene index (modules VBX-xx, accessories, levels, warnings) → GLB package (`userData.vbxId` = stable node id).
- `plans/src/scene/` + `plans/src/viewer/` — loaded model (`LoadedScene`: GLB package + index + module frames) and the three.js viewer (`SceneViewer`): isolation only by `visible = false` (never clipping), ghost neighbours, BVH picking, front-face arrows, offscreen HD captures (MSAA, `LineSegments2` edges, auto-crop via `captureImage.ts`). A GLB node with several materials comes back as a group of primitive meshes: use `meshesOfNode` / `nodeIdOf`.
- `plans/src/core/views.ts` — view bases: world views = SketchUp standard views; module views are relative to the Viewbox frame (Front/Back = short sides, front = short side towards local +X unless overridden, stored in `plans_model_versions.settings.fronts`).
- `plans/src/linework/` — 2D engine behind the `LineworkProvider` seam (`BrowserHlrProvider`): subset → world-baked packet → Web Worker pool (`hlr.worker.ts`) → `hlr.ts` (own edge extraction + three-edge-projection internals for hidden-line removal; glass excluded from occluders; `LineObjectsBVH` needs `heightOffset` = model depth because the library assumes metres) → 2D cleanup (`core/lines2d.ts`: collinear merge, chaining) → layers silhouette/visible/fine/hidden/category:* in model mm → SVG (`svg.ts`, paper-mm strokes). Results cached in IndexedDB (`LINEWORK_ENGINE` in `provider.ts` = cache version: bump it when the engine output changes). Decorations are added after the cache, so they don't change the linework key: `categoryStrokes.ts` (option « Colorer par catégorie », top views: thick legend-colour stroke along the module face) and `facadeMarks.ts` (option `style.facadeMarks` « Repères façade », elevations only: « // » glass hatch on each glass pane visible from the viewer — panes = connected triangles of glass-material meshes, visibility by BVH raycasts, other glass counts as occluder — plus a black corner-to-corner cross on each visible wall item (MUR-*, same visibility test, layer `mark:CROSS`) and door lines copied in their legend colour; layers `mark:<CATEGORY>`, generic glass = `VITRE` « Glass » cyan). Decoration layers are skipped by snapping and auto-dimensioning (`isDecorationLayer`). The sheets `LineworkBank` keys its entries by linework key + decoration flags.
- `plans/src/sheets/` + `plans/src/ui/sheets/` — drawing sets (P3): document model (`types.ts`: sheets of items in paper mm; viewports store a `LineworkRequest`, never linework), Viewbox A1 template measured on the reference LayOut PDFs (`template.ts`; A3 = same template scaled), vector logos traced from those PDFs (`logos.ts`), SVG renderer used for screen/thumbnails/export (`SheetSvg.tsx`), generator reproducing the reference sets (`generate.ts`: cover, 4 views, long/short sides, implantation, per-Viewbox sheet…), Zustand + Immer patch history (`store.ts`), in-memory linework per viewport + stale detection (`bank.ts`). Editor autosaves 2 s after the last change to `plans_drawing_sets` (`data` JSON). Sheet organisation (undoable): thumbnails draggable (`actions.moveSheetTo(id, target, after)`: the sheet joins the target's unit series), ↑ / ↓ / ⧉ / 🗑 on the hovered or active thumbnail, and « Organiser le jeu » in the Planche tab (Monter, Descendre, Déplacer après…, Dupliquer, Supprimer la planche); `moveSheet` at the edge of a unit series first moves the sheet into the neighbouring series (unit + numbering) without changing its place. Title block: project fields (client, address, name, number, date, Sales / Technical / Project manager — `sheets/titleBlock.ts` `projectValues`: project role first, lead first, else the person's VEM role; technical manager from the project record, else the team) are filled at generation from a fresh `GET /projects/:id`, and `DrawingSet.projectSync` keeps the values last taken from the project: on opening a set, fields changed in VEM since then are offered in a banner (`projectChanges`, hand-edited fields are not), and « ↻ Reprendre les données du projet VEM » (Cartouche tab) re-applies them all. 3D images on sheets are rendered by an offscreen `SceneViewer` (`viewer/offscreenCapture.ts`; viewers share `LoadedScene.root`, `reclaim()` re-attaches it) and uploaded as Cloudinary images (`POST /plans/project/:id/assets`). Captures taken in the Vue 3D tab are uploaded the same way (downscaled under 10 MB by `viewer/uploadSize.ts` if needed) and listed in `plans_model_versions.settings.captures` (newest first); clicking an image 3D on a sheet shows them in the properties panel, double-click or « 📷 Image 3D » opens the large picker (`ui/sheets/CapturePicker.tsx`, pure helpers in `sheets/images.ts`). The DRAWING LEGEND lists every category colour (Viewbox legend + custom categories with a colour) on every sheet. Installations in several units: `core/installUnits.ts` `detectUnits` groups Viewbox whose plan footprints (oriented module frames, feet excluded) are ≤ 2.5 m apart (`UNIT_GAP_MM`); each common element goes to the nearest unit within 2.5 m. When ≥ 2 units remain among the selected Viewbox (wizard option « Séparer en unités », names editable), the generator makes an overview series A0.x (cover, 4 views, « Overall aerial view » with unit frames + names = viewport `overlays.units`, overall facades) then every requested sheet per unit; `Sheet.unit` = series A1.x, A2.x… (`renumber` numbers each series), `DrawingSet.units` lists them. World views get « Unités affichées » checkboxes in the viewport properties (any combination of units, for units overlapping in an elevation), applied with « Appliquer »: `setViewportInclude` in `SheetEditor.tsx` computes the new view first, then changes subset + scale + auto dimensions in one undo step. Stacked Viewbox share one number « 1/4 » on top views (`numberLabels`).
- PDF export (P5, `sheets/pdf/`, loaded on demand): « ⬇ PDF du jeu » / « ⬇ PDF planche » in the editor toolbar render each sheet with `SheetSvg` (no editing) and convert it with jsPDF + svg2pdf.js (`pdf.ts` `buildPdf`: one page per sheet at the exact paper size, vector lines/text/logos). Fonts: full static Gelasio / Arimo TTFs in `sheets/pdf/fonts` (OFL, from the Google Fonts CSS API — @fontsource only ships unicode-range subsets), only the variants used are fetched (`fontsUsed`). 3D images (`assets.ts`): PNG when they have transparency (the cover images overlap), else JPEG, max 3000 px. svg2pdf measures text through the browser (`getBBox`): tests polyfill it, and `vite.config.ts` aliases `svg2pdf.js` to its ESM build for Vitest (its UMD `main` expects a global jsPDF).
- DXF export (`sheets/dxf/`, loaded on demand): « ⬇ DXF » in the editor toolbar opens `ui/sheets/DxfDialog.tsx` (displayed sheet = one .dxf; whole set = one .dxf with the sheets side by side left to right, 100 paper mm apart, sheet name above each on layer `VBX-PLANCHES` (`export.ts` `setDxf`, `svgToDxf` options `doc` / `origin` / `label`; in `real` mode each block is at its largest view's scale, sheets without a computed view skipped), or a .zip with one .dxf per sheet via fflate). `svgToDxf.ts` re-reads the same `SheetSvg` markup as the PDF (no `editing`) and converts it element by element: strokes → LWPOLYLINE (lineweight 370 from the paper stroke width, dash arrays → generated linetypes `VBX_TIRETS_…`), circles → CIRCLE, fills → solid HATCH (white fills skipped), texts → TEXT (styles `VBX-SERIF…` / `VBX-SANS…` = georgia*.ttf / arial*.ttf, metric twins of Gelasio / Arimo; height = cap height), nested `<svg>` logos, transforms, rectangular `clip-path` of viewports (Liang-Barsky / Sutherland-Hodgman), 3D images = frame only. Layers come from `data-dxf` attributes set in `SheetSvg` (`VBX-VUE-SILHOUETTE` / `-VISIBLE` / `-FIN` / `-CACHE`, `VBX-CATEGORIE-<cat>`, `VBX-REPERE-<cat>`, `VBX-COTES`, `VBX-CARTOUCHE`, `VBX-CADRE`, `VBX-TITRES`…); category colours are carried by the layer (entities ByLayer). Two modes: `paper` = the whole sheet, 1 unit = 1 mm of paper; `real` = only elements with `data-vp` (viewport content + title, its dimensions, labels anchored to it), each view brought to 1 unit = 1 mm of the model, views laid out as on the sheet (centre × largest scale); sheets without a computed view are skipped. `writer.ts` = own DXF writer, AutoCAD 2007 (AC1021, UTF-8), minimal R2000+ structure (tables VPORT…BLOCK_RECORD, *Model_Space / *Paper_Space, root dictionary + ACAD_GROUP), fixed handles < 0x1000, entities from 0x1000, `$INSUNITS` 4 (mm), `$LWDISPLAY` on. Tests `tests/dxf.test.ts` (`DXF_OUT=dir` keeps the files; check with `python3 -c "import ezdxf; print(ezdxf.readfile(f).audit().errors)"` — ezdxf is not a dependency, pip-install it in the scratchpad); e2e `e2e/run-dxf.mjs`.
- Detail library: fixed vector drawings placed on sheets as `DetailItem` (« ▦ Détail », scale 1:2…1:25 from the frame size, stroke widths constant on paper) in `sheets/details/` — `profiles.ts` (top/bottom profile sections, floor and insulation) is generated from the Spantech reference PDF by `plans/scripts/extract-detail.py` (PyMuPDF; the PDF itself is not in the repo). ### Étude structure (`plans/src/structure/`, phased spec S0–S9)

Internal structural pre-study of a Viewbox installation from the same analysed model (recognition → loads → 3D frame FEM → EC3/EC5/Viewbox joint checks → ground pressure and spreading plates → PDF report). **No number may come from AI**: everything is computed by pure, tested TypeScript. Status: S1 (calculation core), S2 (ground & spreading), S3 (recognition + shared library), S4 (model assembly, loads, combinations), S5 (checks, full calculation and results in the UI), S6 (PDF report FR / DE / EN + A3 calage plan), S7 (AI assistance, composite panels, visible calculation template, birch packing plates), S10 (modified Viewbox, variants, joint revalidation, optimiser) and S11 (custom connections / accessories workshop) done (specs `PROMPT_Etude_Structure_S10_Variantes_Optimisation.md` / `…_S11_Liaisons_Personnalisees.md`, untracked at the repo root); S12 (custom structure types, spec `plans/reference-reports/PROMPT_Etude_Structure_S12_Structures_Personnalisees.md`) in progress: S12.1 safety net, S12.2 generic template, S12.3 per-type data in the calculation and S12.4 structure workshop v1 done. UI: Workspace tab « Étude structure » (`ui/structure/StructurePage.tsx`: step bar 1 Reconnaissance · 2 Site & hypothèses · 3 Calcul · 4 Résultats · 5 Sol & calage · 6 Rapport, each with ✔ / ⚠ / ✖), « 🧮 Calage rapide » in the Modèles page (`QuickGroundPage.tsx`: grid of 5900 Viewbox, levels per slot, no 3D model) and Réglages › « Bibliothèque structure » (`LibraryPage.tsx`: list / search / detail / edit data as JSON / disable / delete = back to seed / export / import).
- Units inside `structure/`: **N, mm, N/mm², rad** only; conversions (`KN`, `KNM`, `KN_PER_CM`, `KNCM_PER_DEG`…, French formatting `fmt`) in `core/units.ts`, used for input/display only. Global frame = SceneIndex (mm, Y up); the report will show Z up.
- `core/fem/` — 3D frame solver: `element.ts` (Euler-Bernoulli 12-DOF element; end releases and springs per local DOF (`EndSpec`: 'rigid' | 'free' | stiffness) removed by static condensation, no penalty; equivalent loads from Hermite shape functions; geometric stiffness; internal forces along the member with P-δ from the Hermite deflection). Sign convention: N tension +, My / Mz positive when the −z / −y fibre is in tension (sagging positive), σ = N/A − My·z/Iy − Mz·y/Iz. `ordering.ts` (minimum degree / geometric nested dissection / RCM at node level, the cheapest factorization wins — minimum degree in practice), `sparse.ts` (6×6 block LDLᵀ, Davis up-looking; a zero / negative pivot is reported as mechanism / 2nd-order instability with the node), `analysis.ts` (`prepare(model)` once per model — segmentation `segments`, ordering, symbolic — then `analyzeLoadSet` per combination: supports fixed / spring / compression-only with uplift releasing Y or all translations, tension- / compression-only members toggled until stable (violations measured as forces, tolerance `contactTolerance` 1 N; one change at a time after 10 iterations or once a state repeats; a persistent cycle keeps the best state if its residual is negligible, with a warning; a trial state that is unstable is undone and retried with one change — if a single uplift / contact opening makes the structure unstable it is reported as « Stabilité d'ensemble non assurée »), 2nd order by iterating Kg(N); `geometric: false` = connector without geometric stiffness (10 mm bolts / contacts would otherwise buckle as pendulums); translations > 10 m are reported as a near-mechanism). A node rotation that no member restrains (all ends released) is a decoupled zero-energy mode and is stabilised, not reported. Reactions = Σ member end forces − nodal loads.

### Frontend (`public/`)

- `public/index.html` is the shell (nav, layout, modals markup) and loads 15 sequential, non-module `<script>` files from `public/js/01-core.js` through `15-checklists.js` — load order matters, they share globals (no bundler, no ES modules). Numbered prefix = load order, not strict feature grouping (e.g. auth code lives in `07-auth-mobile-daily-ai.js`, not `01-core.js`).
- Heavy third-party libs (`jspdf`, `fabric`) are loaded with `defer` from CDN in the `<head>` of `index.html`, not bundled.
- `public/js/11-briefing.js` through `14-briefing-autogen.js` implement "Briefing Studio", a Fabric.js-based slide editor (copy/paste, slide duplication, text boxes) used to prep on-site briefings; it's the most actively-changing part of the frontend.
- `public/sign-handover.html` — standalone public page for client handover signature (served alongside the main SPA, not part of the JS bundle chain).
- `public/planning-public.html` — standalone public read-only planning display (paired with the `publicCalendar` API route).
- `public/viewer3d.html` + `public/vem-3d-integration.js` — embeddable 3D viewer (Three.js r128, loaded from CDN) supporting IFC (via `web-ifc`) and COLLADA `.dae` (via `ColladaLoader`), both loaders fetched dynamically at runtime rather than bundled. Model/asset files themselves are pulled from jsDelivr (`cdn.jsdelivr.net/gh/amaurypinchart-VBX/3Dviewer@main/...`) — `raw.githubusercontent.com` is blocked by CORS for this use case, jsDelivr is not optional.

### Data model (`prisma/schema.prisma`)

Central entity is `Project` (status flows through the `ProjectStatus` enum: draft → confirmed → quote states → in_preparation → loading → on_site → installation → handover → handover_ok → dismantling → completed, or cancelled). Everything else hangs off a project: `Task`/`TaskTemplate`/`TaskCategory`, `Ticket`, `Handover`, `DailyReport`, `ClientVisit`/`ClientRemark`, `TeamBooking`/`HotelBooking`, `Truck`, `Briefing`, plus warehouse (`WarehouseBox`, `Toolbox`) and `Client`/`ClientContact`. `User.role` (`UserRole` enum: admin, project_manager, site_manager, technical_manager, engineer, worker, client, warehouse, sales_engineer, installer) drives access control — role-based restriction of *which projects* a given role can see (beyond simple auth) is an ongoing, partially-implemented effort: `src/middleware/projectAccess.ts` (`assertProjectAccess`: installer and site_manager only see projects where they are in the team or technical manager) is so far used only by the checklist routes; check each route file individually rather than assuming role checks are consistent across `projects.ts`, `clientVisits.ts`, `handover.ts`, `dailyReports.ts`, etc.

### Common gotchas

- Cascading 401s across every endpoint at once is almost always an expired JWT, not a code regression — the fix is re-authenticating, not debugging the backend.
- Prisma unique-constraint (`P2002`) fixes sometimes require `ALTER TABLE ... DROP CONSTRAINT` rather than `DROP INDEX`, when the index backs a constraint rather than existing standalone.
